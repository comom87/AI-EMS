# AI-EMS MLOps 플랫폼

## 개요

AI-EMS MLOps 플랫폼은 전력 계통 운영(EMS)에 활용하는 머신러닝 모델의 개발, 배포, 운영을 지원하는 공용 MLOps 플랫폼입니다.
여러 모델 개발자가 각자의 모델을 표준화된 절차에 따라 운영 환경에 배포하고, 응용 프로그램은 서빙 API를 통해 모델의 예측 결과를 활용합니다.
데이터 수집부터 학습, 평가, 승격, 서빙, 운영 중 점검, 재학습에 이르는 모델 생애주기 전반을 하나의 자동화된 흐름으로 관리합니다.

## 도입 배경

- **모델 운영 방식의 표준화:** 모델마다 학습과 배포 방식이 달라지면 운영과 유지보수 부담이 커집니다. 본 플랫폼은 모든 모델이 동일한 생애주기를 따르도록 하고, 모델별 구현은 기능 폴더 단위로 분리합니다.
- **검증된 모델만 운영 반영:** 신규 모델은 현재 운영 중인 모델(champion)과 동일한 시험 데이터로 비교 평가하며, 성능이 우수한 경우에만 운영에 반영합니다.
- **운영 중 품질 관리:** 계통 데이터의 분포 변화나 예측 성능 저하를 지속적으로 감시하고, 기준을 벗어나면 재학습을 자동으로 수행합니다.
- **한정된 GPU 자원의 공동 활용:** 여러 사용자의 학습 작업을 Slurm으로 스케줄링하고, MPS를 이용해 GPU 한 장을 여러 작업이 나누어 사용합니다.

## 주요 기능

| 기능 | 설명 |
|---|---|
| 파이프라인 조립 | Airflow 파이프라인을 YAML로 정의합니다. 모델별로 단계, 순서, 실행 주기, 판단 기준을 코드 수정 없이 구성할 수 있습니다 |
| 데이터 등록과 피처 저장소 | 데이터 소스의 신규 데이터를 주기적으로 등록하고, Feast 온라인 저장소(Redis)에 최신 피처를 반영합니다 |
| GPU 학습 작업 관리 | 학습·평가를 Slurm 작업으로 실행하며, 이전 사용량을 기반으로 GPU·CPU·메모리 할당량을 자동 산정하고 사용 이력을 기록합니다 |
| 실험 및 모델 관리 | 학습·평가 결과와 모델 버전을 MLflow에 기록하고, 운영 모델을 champion 별칭으로 관리합니다 |
| 비교 평가 기반 승격 | 후보 모델과 champion을 동일한 시험 데이터로 평가하여, 지정한 지표가 우수할 때만 승격합니다 |
| 통합 서빙 | 하나의 서빙 API에서 모든 모델의 champion을 제공하며, 모델 교체와 신규 모델 추가를 서비스 재시작 없이 반영합니다 |
| 운영 점검과 재학습 | 예측이 저장될 때마다 성능 저하와 입력 분포 변화를 점검하고, 필요 시 학습 파이프라인을 자동 실행합니다 |
| 모니터링 | 점검 결과, 학습 이력, GPU 사용량을 Grafana 대시보드로 제공합니다 |

## 시스템 흐름

```
등록 DAG (5분 주기) ── 신규 데이터 ──▶ PostgreSQL ──▶ Redis (Feast 온라인 저장소)
                                                          │ 최신 입력
외부 시스템 ── POST /models/<모델>/predict ──▶ 서빙 API ──┘
                                                 │ 예측 저장 및 신호
                                                 ▼
                                 점검 DAG: 성능·입력 분포 점검 ──(기준 초과 시)──▶ 학습 DAG
                                                                                  │
              서빙: 1분 이내 신규 champion 반영 ◀── 우수 시 승격 ◀── Slurm GPU 학습·평가
```

1. **데이터 등록:** 데이터 소스의 신규 데이터를 5분 주기로 데이터베이스에 등록하고, 서빙에서 사용할 최신 피처를 Redis에 반영합니다.
2. **학습:** 정기 일정 또는 재학습 요청에 따라 학습 데이터를 준비·검증한 후, Slurm에서 학습과 평가를 수행합니다. 결과는 MLflow에 기록됩니다.
3. **승격:** 후보 모델의 평가 지표가 champion보다 우수한 경우에만 champion으로 승격합니다.
4. **서빙:** 외부 시스템의 요청에 대해 champion 모델로 예측하고 결과를 저장합니다.
5. **점검 및 재학습:** 예측이 저장될 때마다 최근 성능과 입력 분포를 점검하고, 기준을 벗어나면 학습 파이프라인을 실행합니다.

## 역할 구분

| 역할 | 담당 영역 | 주요 업무 |
|---|---|---|
| 운영자 | `data/`, `common/`, `dags/`, `serving/`, `infra/` | 데이터 소스 등록, 공용 플랫폼(학습 작업 제출, 승격, 서빙, 점검) 개발 및 서비스 운영 |
| 모델 개발자 | `sources/<기능>/` (기능 하나당 모델 하나) | 학습 데이터 준비, 학습·평가 구현, 예측 코드, 분포 비교 기준, 파이프라인 정의 |
| 응용 개발자 | 서빙 API | `POST /models/<모델>/predict`를 호출하여 예측 결과 활용 |

신규 모델은 `template/`을 복사하여 기능 폴더를 생성하고 정해진 함수를 구현하는 방식으로 추가합니다. 추가된 모델은 서비스 재시작 없이 Airflow(5분 이내)와 서빙(1분 이내)에 자동으로 반영됩니다. 파이프라인을 구성하기 전에 직접 학습한 모델을 먼저 서빙하는 방식도 지원합니다.

## 기술 스택

| 구성 요소 | 용도 |
|---|---|
| Apache Airflow | 파이프라인(DAG) 실행 및 스케줄링 |
| Slurm, Apptainer | GPU 학습·평가 작업 스케줄링 및 컨테이너 실행 |
| MLflow | 실험 기록, 모델 레지스트리 |
| PostgreSQL | 데이터, 예측 기록, 점검·작업 이력, Feast 오프라인 저장소 |
| Redis, Feast | 온라인 피처 저장소 |
| FastAPI | 모델 서빙 API |
| Grafana | 운영 모니터링 대시보드 |

모든 서비스는 단일 서버에서 Docker Compose(`infra/docker-compose.yml`)로 구동하며, 학습 작업은 Slurm을 통해 실행합니다.

## 현재 구성

| 구분 | 이름 | 설명 |
|---|---|---|
| 데이터 소스 | `kpg193` | KPG193 계통(모선 193개)의 최적 조류(OPF) 시나리오. 원본 9,994개를 5분 주기로 실시간 데이터에 등록 |
| 모델 | `optimal_power_flow` | KPG193 실시간 시나리오를 입력으로 최적 조류를 예측하는 gridfm-graphkit 기반 GNN 모델 |
